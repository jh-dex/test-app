# Live Board 실시간 협업 기술 검토

검토일: 2026-06-14

대상: `C:\Users\hoon\Desktop\claude\test-app`

## 결론

현재 구현은 "여러 PC가 같은 보드에 접속해서 최종 결과를 공유하는 MVP"로는 의미가 있습니다. 하지만 사용자가 기대하는 "피그마처럼 다른 화면에서도 바로바로, 매끄럽게 움직임이 보이는 협업 도구" 기준에는 아직 부족합니다.

가장 큰 이유는 이미지/텍스트/비교 박스의 이동과 리사이즈가 드래그 중에는 다른 PC로 전송되지 않고, 마우스를 놓는 순간에만 최종 상태가 전송되기 때문입니다. 그림 그리기는 중간 점을 전송하므로 비교적 실시간에 가깝지만, 객체 편집은 피그마식 체감이 아니라 "놓은 뒤 순간 반영"에 가깝습니다.

현재 상태 평가:

- 실시간 드로잉: 보통. 중간 stroke 전송과 최종 stroke 보정이 있음.
- 이미지/텍스트/박스 이동: 부족. 드래그 중 실시간 전송이 없음.
- 동시 편집 안정성: 부족. 객체별 버전, 순서 보장, 충돌 처리 없음.
- Render 무료 테스트 적합성: 짧은 MVP 테스트는 가능. 상태 보존과 콜드 스타트에는 취약.
- 사용성: 기능은 많지만, 협업 체감과 장애 복구 안내가 부족.

## 현재 동기화 구조

이 앱은 WebSocket이 아니라 다음 방식으로 동작합니다.

- 서버 -> 클라이언트: SSE `GET /events` (`server.js:59`)
- 클라이언트 -> 서버: HTTP `POST /sync` (`server.js:81`)
- 같은 브라우저의 여러 탭: `BroadcastChannel` (`app.js:1-7`)
- 늦게 들어온 사용자 보정: 클라이언트가 전체 보드 스냅샷 `state-store`를 보내고, 서버가 메모리에 `boardSnapshot`으로 저장 (`app.js:226-243`, `server.js:23-26`, `server.js:99-100`)

이 구조는 간단하고 배포하기 쉽습니다. 다만 피그마처럼 높은 빈도의 상호작용을 부드럽게 보여주기에는 HTTP POST 기반 왕복, 순서 보장 부재, 재시도 부재가 병목이 됩니다.

JS 문법 검사는 통과했습니다.

- `node --check server.js`: 통과
- `node --check app.js`: 통과

## 좋은 점

1. 그림 그리기는 중간 업데이트와 최종 보정을 같이 사용합니다.
   - `stroke-append`로 그리는 중간 점을 보냅니다 (`app.js:2262`).
   - `stroke-end`에서 전체 stroke points를 다시 보내 누락된 중간 메시지를 보정하려고 합니다 (`app.js:2363-2369`).

2. 지우개도 최종 경로 보정을 시도합니다.
   - 중간에는 `erase-segment`를 보내고, 종료 시 `erase-path` 전체를 보냅니다 (`app.js:2247-2255`, `app.js:2338-2342`).

3. 늦게 접속한 사용자를 위한 전체 스냅샷 개념이 있습니다.
   - 서버가 최신 `boardSnapshot`을 저장했다가 새 SSE 연결에 `board-state`로 내려줍니다 (`server.js:69-72`).

4. 클라이언트 전송을 프레임 단위로 묶으려는 시도가 있습니다.
   - `outboundQueue`와 `requestAnimationFrame`으로 여러 메시지를 한 번의 `POST /sync`로 묶습니다 (`app.js:170-193`).

이런 점들은 MVP 방향성으로는 괜찮습니다. 문제는 "움직이는 동안의 상태", "순서", "충돌", "복구"입니다.

## 주요 문제점

### 1. 드래그 중 실시간 이동/리사이즈가 전송되지 않음

심각도: 매우 높음

`pointerMove`에서 이미지, 텍스트, 비교 박스, 그룹의 위치와 크기를 로컬 DOM에만 반영하고 `silent: true`로 처리합니다.

관련 코드:

- 그룹 이동: `app.js:2050-2082`
- 그룹 리사이즈: `app.js:2085-2118`
- 텍스트 이동: `app.js:2144-2156`
- 비교 박스 이동/리사이즈: `app.js:2171-2202`
- 이미지 이동/리사이즈: `app.js:2208-2229`

다른 PC로 실제 전송되는 시점은 `pointerUp`입니다.

- 그룹 이동 완료 후 전송: `app.js:2281-2294`
- 그룹 리사이즈 완료 후 전송: `app.js:2296-2309`
- 텍스트 이동/리사이즈 완료 후 전송: `app.js:2311-2316`
- 비교 박스 완료 후 전송: `app.js:2317-2322`
- 이미지 완료 후 전송: `app.js:2323-2328`

사용자 체감:

- A PC에서 이미지를 드래그하는 동안 B PC에서는 이미지가 가만히 있음.
- A PC가 마우스를 놓으면 B PC에서 이미지가 갑자기 최종 위치로 이동함.
- 피그마처럼 "상대방이 움직이는 장면이 계속 보이는" 느낌이 나오지 않음.

개선 방향:

- `pointermove` 중에도 `image-drag`, `text-drag`, `compare-drag`, `group-drag` 같은 임시 업데이트를 30~60fps 또는 16~33ms throttle로 전송해야 합니다.
- `pointerup`에서는 최종 확정 메시지 `image-commit`, `text-commit` 등을 보내야 합니다.
- 원격 화면에서는 임시 업데이트를 즉시 적용하되, CSS transform 기반으로 반영하면 레이아웃 비용을 줄일 수 있습니다.
- 더 부드럽게 보이려면 원격 객체 이동에 짧은 보간(interpolation)을 적용합니다. 예: 마지막 위치에서 새 위치까지 80~120ms 안에 따라가기.

### 2. 전송 실패를 무시하고 재시도하지 않음

심각도: 높음

`fetch('/sync')` 실패가 발생해도 catch에서 아무 작업도 하지 않습니다.

관련 코드:

- `app.js:187-193`

문제:

- 노트북 와이파이가 순간적으로 끊기거나 Render가 재시작하면 변경 이벤트가 사라집니다.
- 실패한 메시지를 다시 보내는 큐가 없습니다.
- 사용자는 "내 화면에서는 바뀌었는데 다른 PC에는 안 바뀐" 상태를 겪을 수 있습니다.

개선 방향:

- 전송 메시지에 `clientId`, `clientSeq`, `objectId`, `objectVersion`을 넣습니다.
- 실패한 메시지는 pending queue에 남기고 지수 백오프(exponential backoff)로 재전송합니다.
- 서버가 받은 마지막 sequence를 ACK로 알려주도록 합니다.
- 단기적으로는 실패 시 `outboundQueue` 앞쪽에 다시 넣는 것만으로도 유실을 줄일 수 있습니다.

### 3. 메시지 순서 보장이 없음

심각도: 높음

현재 클라이언트는 프레임마다 `POST /sync`를 만들 수 있고, 이전 POST가 끝나기 전에 다음 POST가 먼저 도착할 수 있습니다. 서버는 도착한 순서대로 그대로 브로드캐스트합니다.

관련 코드:

- 클라이언트 전송: `app.js:177-193`
- 서버 브로드캐스트: `server.js:96-103`
- 수신 적용: `app.js:2814-2927`

문제:

- 위치 100 -> 200 -> 300 순서로 움직였는데 네트워크 상황에 따라 300이 먼저 도착하고 200이 나중에 도착할 수 있습니다.
- 원격 PC는 최신 위치를 오래된 위치로 되돌릴 수 있습니다.
- 현재 `seenMessageIds`는 중복 제거만 하고, "이 메시지가 최신인가?"는 판단하지 않습니다.

개선 방향:

- 객체별 revision 또는 Lamport clock을 둡니다.
- 클라이언트는 `objectVersion`이 현재보다 낮은 업데이트를 버려야 합니다.
- 서버가 방(room)별 `serverRevision`을 부여하고, 클라이언트가 revision 순서대로 적용하는 구조가 더 안전합니다.

### 4. 전체 스냅샷이 오래된 상태로 덮일 수 있음

심각도: 높음

변경 후 400ms 뒤 클라이언트가 전체 보드 상태를 `state-store`로 서버에 저장합니다. 서버는 이 값을 검증 없이 `boardSnapshot`에 덮어씁니다.

관련 코드:

- 클라이언트 스냅샷 예약: `app.js:238-243`
- 서버 스냅샷 저장: `server.js:99-100`

문제:

- A 사용자가 최신 상태를 만들었는데, B 사용자의 오래된 스냅샷이 늦게 도착하면 서버의 최신 보드가 과거 상태로 돌아갈 수 있습니다.
- 기존 접속자는 이벤트로 어느 정도 맞을 수 있지만, 새로 들어온 사용자는 잘못된 스냅샷을 받을 수 있습니다.

개선 방향:

- 스냅샷에 `baseRevision` 또는 `snapshotRevision`을 넣고, 서버는 현재 revision보다 오래된 스냅샷을 거부해야 합니다.
- 더 안정적인 구조는 "서버가 이벤트 로그를 받고 직접 최신 스냅샷을 생성"하는 방식입니다.
- 클라이언트가 임의로 전체 스냅샷을 덮어쓰는 구조는 협업 앱에서 위험합니다.

### 5. 드로잉 변경 감지 fingerprint가 부정확함

심각도: 높음

`makeHistoryFingerprint`는 그림 상태를 `drawingOps.length`만으로 반영합니다.

관련 코드:

- `app.js:1270-1280`

문제:

- 지우개로 stroke 일부를 잘라냈는데 `drawingOps.length`가 우연히 같으면 변경이 감지되지 않을 수 있습니다.
- `pushHistory`가 변경 없음으로 판단하면 서버 스냅샷 저장도 건너뜁니다 (`app.js:1329-1349`).
- 그 결과 현재 접속자끼리는 `erase-path` 이벤트로 맞아 보일 수 있지만, 나중에 들어온 사용자는 지워지기 전 그림을 받을 수 있습니다.

개선 방향:

- fingerprint에 stroke id, color, size, tool, points 좌표를 포함해야 합니다.
- 또는 드로잉이 바뀔 때마다 별도 `drawingRevision`을 증가시키고 fingerprint에 포함합니다.

### 6. Render 무료 환경에서는 메모리 상태가 쉽게 사라짐

심각도: 높음

서버의 보드 상태는 `boardSnapshot` 변수 하나입니다.

관련 코드:

- `server.js:23-26`

Render 공식 문서 기준 주의점:

- Free Web Service는 15분 동안 inbound traffic이 없으면 sleep 상태가 됩니다. 다음 접속 시 다시 뜨는 데 약 1분이 걸릴 수 있습니다.  
  참고: https://render.com/docs/free
- Render의 Free Web Service는 재시작, 재배포, sleep 이후 로컬 파일 변경이 유지되지 않는 ephemeral filesystem 환경입니다. 이 앱은 파일 저장은 하지 않지만, 메모리 상태인 `boardSnapshot`도 서버 프로세스가 재시작되면 사라집니다.
- Free Web Service는 언제든 재시작될 수 있고, scaling은 단일 인스턴스만 가능합니다.

사용자 체감:

- 잠깐 테스트하다가 시간이 지나 다시 접속하면 보드가 초기화될 수 있습니다.
- Render 콜드 스타트 때문에 첫 접속자가 약 1분 기다릴 수 있습니다.
- 서버 재시작 중에는 SSE 연결이 끊기고, 클라이언트가 재접속하더라도 서버 메모리 상태는 비어 있을 수 있습니다.

개선 방향:

- 테스트용이라도 상태를 Render Postgres 같은 외부 저장소에 저장하는 것이 좋습니다.
- 단, Render Free Postgres는 30일 제한과 백업 없음 등 제약이 있으므로 장기 사용에는 유료 DB 또는 다른 관리형 DB가 필요합니다.
- Redis/Key Value는 presence, 커서, 임시 세션에는 적합하지만, Render Free Key Value는 in-memory only라 재시작 시 데이터가 사라집니다.

### 7. 이미지가 base64 Data URL로 전체 동기화됨

심각도: 중간~높음

이미지 업로드 시 `FileReader.readAsDataURL`로 파일 전체를 base64 문자열로 만들어 payload에 넣습니다.

관련 코드:

- 이미지 import: `app.js:2687-2704`
- 이미지 payload serialize: `app.js:850-860`
- 서버 POST 제한: `server.js:83-87`

문제:

- base64는 원본보다 대략 33% 커집니다.
- 큰 이미지 몇 장을 올리면 `POST /sync` payload와 `boardSnapshot`이 매우 커집니다.
- 서버 제한은 30MB이므로 큰 이미지나 여러 장의 이미지에서 동기화 실패가 발생할 수 있습니다.
- 새 사용자가 들어올 때 전체 스냅샷으로 큰 이미지 데이터가 한 번에 내려가 초기 로딩이 느려집니다.

개선 방향:

- 이미지는 별도 업로드 API로 저장하고, 보드 상태에는 이미지 URL과 메타데이터만 저장합니다.
- 최소한 클라이언트에서 이미지 리사이즈/압축 후 업로드해야 합니다.
- Render에서 테스트하려면 S3, Cloudflare R2, Supabase Storage 같은 외부 object storage를 붙이는 방향이 적절합니다.

### 9. 동시 편집 충돌 처리 없음

심각도: 중간~높음

현재는 같은 객체를 두 명이 동시에 편집하면 마지막에 도착한 업데이트가 덮어씁니다.

관련 코드:

- 원격 업데이트 적용: `app.js:2914-2919`
- 텍스트 입력 throttle: `app.js:899-906`
- 텍스트 remote 적용: `app.js:994-998`

문제:

- 두 사용자가 같은 텍스트를 동시에 편집하면 한쪽 입력이 사라질 수 있습니다.
- 같은 이미지를 동시에 움직이면 위치가 튀거나 최종 위치가 예측하기 어렵습니다.
- 상대가 지금 선택/편집 중인 객체를 보여주지 않아 충돌을 피하기 어렵습니다.

개선 방향:

- 최소 구현: 원격 선택 표시와 "다른 사용자가 편집 중" 잠금 표시.
- 더 좋은 구현: 객체별 soft lock, stale lock timeout.
- 텍스트 공동 편집까지 피그마 수준으로 하려면 CRDT/Yjs 같은 협업 텍스트 엔진 검토가 필요합니다.

### 10. WebSocket을 쓰지 않는 구조는 피그마식 체감에 불리함

심각도: 중간

Render는 WebSocket을 지원합니다. 공식 문서에서도 Node.js에서 `ws` 모듈을 붙이는 방식을 안내하고, public 인터넷에서는 `wss://` 사용을 권장합니다.  
참고: https://render.com/docs/websocket

현재 SSE + POST 방식도 소규모 MVP는 가능합니다. 하지만 실시간 협업 툴에서는 다음 이유로 WebSocket이 더 적합합니다.

- 하나의 연결에서 양방향 메시지를 지속적으로 주고받을 수 있음.
- POST 요청을 매 프레임 만들 필요가 없어 오버헤드가 낮음.
- ping/pong, reconnect, backpressure, ACK를 구현하기 쉬움.
- 서버가 room별 revision을 부여하고 즉시 브로드캐스트하기 좋음.

개선 방향:

- 단기 테스트는 현재 구조를 보완해도 됩니다.
- 피그마처럼 만들 계획이면 WebSocket 기반으로 재설계하는 것이 좋습니다.

### 11. 입력 검증과 방어 코드가 부족함

심각도: 중간

서버는 들어온 메시지 타입과 payload 구조를 거의 검증하지 않고 그대로 브로드캐스트합니다.

관련 코드:

- `server.js:90-103`

클라이언트도 `board-state` payload를 강하게 검증하지 않고 복원합니다.

관련 코드:

- `app.js:1299-1327`
- `app.js:2927`

문제:

- 잘못된 payload가 들어오면 특정 클라이언트에서 에러가 날 수 있습니다.
- 악의적 사용자가 큰 payload를 반복 전송하면 서비스가 느려질 수 있습니다.
- `Access-Control-Allow-Origin: *`라 외부 사이트에서도 이 서버로 POST를 보낼 수 있습니다 (`server.js:64`, `server.js:106`).

개선 방향:

- 메시지 타입별 schema validation을 추가합니다.
- room token 또는 origin 제한을 둡니다.
- payload 크기 제한을 타입별로 나눕니다.
- 비정상 메시지를 서버에서 폐기하고 로그를 남깁니다.

### 12. 로컬 Git 저장소가 정상 상태가 아님

심각도: 중간

폴더에 `.git` 디렉터리는 있지만 `git status`가 실패합니다. 확인 결과 `.git/objects`가 없습니다.

영향:

- Render를 GitHub 저장소와 연동해 자동 배포할 때 로컬 변경 추적이 꼬일 수 있습니다.
- 실제 GitHub에 올라간 코드와 로컬 폴더 코드가 다를 위험이 있습니다.

개선 방향:

- 현재 폴더를 새 Git 저장소로 다시 초기화하거나, 정상 GitHub repo를 다시 clone하는 것이 좋습니다.
- Render에 배포하기 전 `git status`, `git remote -v`, GitHub 웹의 최신 파일 내용을 반드시 확인해야 합니다.

## Render 무료 서비스에서 테스트할 때의 현실적인 기대치

Render Free Web Service는 "빠르게 링크를 만들어 지인/다른 PC에서 테스트"하기에는 적합합니다. 하지만 다음 현상은 정상으로 봐야 합니다.

- 첫 접속이 느릴 수 있음: 15분 idle 후 sleep, 다음 요청에서 약 1분 cold start 가능.
- 서버 재시작/재배포/슬립 후 메모리 보드 상태가 사라질 수 있음.
- 무료 대역폭/빌드/인스턴스 시간 제한에 걸릴 수 있음.
- 큰 이미지와 잦은 실시간 이벤트는 무료 인스턴스에서 버벅일 수 있음.

따라서 Render 무료 환경에서 테스트 목표를 이렇게 잡는 것이 좋습니다.

- "두 PC가 같은 URL로 접속 가능한가?"
- "그림이 그리는 중에 반대편에 보이는가?"
- "이미지를 이동하는 중에도 반대편에 따라 보이는가?"
- "새로고침/재접속/새 사용자 접속 후에도 같은 상태가 보이는가?"
- "서버가 잠들었다 깨어난 뒤 데이터가 어떻게 되는가?"

현재 코드 그대로는 세 번째와 네 번째 항목에서 만족도가 낮을 가능성이 큽니다.

## 피그마식 실시간성을 위한 권장 구조

권장 아키텍처:

1. 클라이언트는 WebSocket으로 room에 접속합니다.
2. 모든 변경은 operation 단위로 보냅니다.
   - 예: `object.drag`, `object.resize`, `object.commit`, `stroke.append`, `stroke.end`, `text.update`
3. 서버는 room별로 `serverRevision`을 증가시키고 operation에 revision을 붙입니다.
4. 서버는 operation을 같은 room의 다른 클라이언트에 즉시 broadcast합니다.
5. 클라이언트는 revision이 낮은 메시지를 버리고, 누락이 있으면 snapshot 재요청을 합니다.
6. 서버는 일정 주기 또는 operation N개마다 snapshot을 DB에 저장합니다.
7. 이미지는 object storage에 저장하고, 보드에는 URL만 보관합니다.

필수 데이터 예시:

```json
{
  "roomId": "abc",
  "clientId": "client-1",
  "clientSeq": 42,
  "serverRevision": 128,
  "type": "object.drag",
  "objectId": "image-123",
  "objectVersion": 17,
  "payload": {
    "x": 120,
    "y": 240
  }
}
```

이 구조가 있어야 다음을 안정적으로 처리할 수 있습니다.

- 메시지 순서 뒤바뀜
- 네트워크 순간 끊김
- 새 사용자 접속
- 동시에 같은 객체 편집
- 서버 재시작 후 복구

## 개선 우선순위

### 1단계: 지금 MVP를 테스트 가능한 수준으로 보강

우선순위: 가장 높음

- 이동/리사이즈 중간 상태를 throttle해서 전송.
- 객체별 `version` 또는 `updatedAt`을 추가하고 오래된 업데이트 무시.
- `fetch('/sync')` 실패 시 재시도 큐 추가.
- 드로잉 fingerprint를 `drawingOps.length`가 아니라 실제 points 기반으로 변경.
- `board-state` payload 방어 코드 추가.
- room ID 최소 구현 추가.

이 단계만 해도 "다른 PC에서 바로바로 바뀌는 느낌"이 크게 개선됩니다.

### 2단계: Render 테스트 안정화

우선순위: 높음

- 보드 snapshot을 DB에 저장.
- 이미지 base64 전송을 줄이고 외부 storage URL 방식으로 변경.
- Render 배포 전 Git 저장소 정상화.
- Render cold start와 데이터 유실을 README에 명확히 안내.
- 간단한 상태 표시 추가: 연결됨, 재연결 중, 오프라인, 동기화 실패.

### 3단계: 피그마식 협업 품질로 재설계

우선순위: 중장기

- WebSocket 기반 room server로 전환.
- 서버 revision, ACK, reconnect backoff, snapshot resync 구현.
- 원격 커서와 원격 선택 표시.
- 객체별 soft lock 또는 충돌 표시.
- 텍스트 공동 편집이 중요하면 Yjs 같은 CRDT 도입 검토.
- Playwright 같은 자동화로 2개 브라우저 동시 편집 테스트 작성.

## 테스트 체크리스트

Render 배포 후 아래를 실제 PC 2대 또는 브라우저 2개에서 확인해야 합니다.

1. A에서 펜으로 천천히 선을 그릴 때 B에서 선이 실시간으로 보이는가?
2. A에서 빠르게 선을 그릴 때 B에서 점이 빠지거나 나중에 보정되는가?
3. A에서 이미지를 드래그하는 동안 B에서도 이미지가 따라 움직이는가?
4. A에서 이미지 크기를 조절하는 동안 B에서도 크기가 따라 바뀌는가?
5. A와 B가 같은 이미지를 동시에 움직이면 최종 위치가 예측 가능한가?
6. A에서 텍스트를 입력하는 동안 B에서 텍스트가 자연스럽게 보이는가?
7. A와 B가 같은 텍스트를 동시에 수정하면 내용이 사라지지 않는가?
8. A에서 이미지를 1MB, 5MB, 10MB로 올렸을 때 B의 로딩 속도와 안정성은 어떤가?
9. C가 나중에 접속했을 때 A/B가 보던 최신 보드와 같은가?
10. 브라우저 새로고침 후에도 상태가 유지되는가?
11. Render 서비스가 sleep 후 깨어났을 때 보드 상태가 유지되는가?
12. 네트워크를 잠깐 끊었다가 다시 연결했을 때 누락 없이 복구되는가?

## 비개발자 관점의 합격 기준

피그마처럼 보인다고 말하려면 최소한 아래 기준을 만족해야 합니다.

- 상대방이 이미지를 움직이면 내 화면에서도 0.1~0.2초 이내에 움직임이 시작된다.
- 마우스를 놓을 때만 순간 이동하는 것이 아니라, 드래그 중 계속 따라온다.
- 연결이 끊기면 화면에 "재연결 중" 같은 상태가 표시된다.
- 새로 들어온 사람도 현재 보드를 정확히 본다.
- 큰 이미지 몇 장을 올려도 앱이 멈추지 않는다.
- 두 명이 동시에 작업해도 보드가 예측 불가능하게 되돌아가지 않는다.

현재 구현은 이 기준 중 "드래그 중 계속 따라온다", "새로 들어온 사람도 항상 정확히 본다", "동시에 작업해도 안정적이다"를 만족하지 못할 가능성이 큽니다.

## 최종 권고

Claude가 만든 현재 버전은 MVP 시작점으로는 괜찮습니다. 특히 드로잉 이벤트와 늦은 접속자용 snapshot 아이디어는 방향이 맞습니다. 하지만 "피그마처럼 매끄러운 실시간 협업"이라는 목표를 달성하려면 실시간 동기화 계층을 더 엄격하게 만들어야 합니다.

가장 먼저 고쳐야 할 것은 세 가지입니다.

1. 드래그/리사이즈 중에도 원격 화면에 계속 업데이트 보내기.
2. 메시지 순서와 객체 버전을 관리해서 오래된 업데이트가 최신 상태를 덮지 못하게 하기.
3. Render 재시작/슬립 후에도 보드 상태가 유지되도록 DB 또는 외부 저장소 붙이기.

이 세 가지가 해결되기 전에는 Render에 올려 테스트하더라도 "두 PC가 연결은 되지만 피그마처럼 부드럽지는 않다"는 평가가 나올 가능성이 높습니다.
